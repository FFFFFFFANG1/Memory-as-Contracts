# CCTU Noise Evaluator Human Fix

This note records how the MAC-CCTU noisy evaluators were generated, what the
first verification pass reported, what `noise_eval_verify.py` checks, and how
the flagged evaluator code was repaired. The verifier itself was not modified
during the repair pass.

## Initial Evaluator Generation

The original noisy evaluator artifacts were generated by
`bench/construct/cctu/noise_eval_generation.py` into:

- `bench/MAC/cctu/data/noise_check_code/`
- `bench/cctu/mid_data/eval_step5_noise_eval_specs.json`

The generator created one evaluator artifact per MAC-CCTU graph node. Each
artifact answers only this question:

```text
Did the executed agent trajectory appear to follow this single constraint?
```

It does not decide whether the constraint should apply. The graph oracle
provides that label separately through `expected_should_apply`.

Generation used three sources, in this order:

1. `cctu_reference`: for CCTU anchor constraints, reuse or wrap the original
   CCTU `check_code` artifacts when available.
2. `heuristic`: for obvious local patterns such as response format, response
   length, total tool calls, per-tool call counts, tool usage, tool sequence,
   and parallel tool use.
3. `llm`: for constraints not covered by the local rulebase. The LLM received
   only compact information: constraint text, weak type hint, and available
   tool names. Stable IDs, artifact paths, graph labels, and metadata were
   filled locally.

The first full generation summary was:

After `noise_eval_verify.py` was added and run on all generated artifacts, the
first audit reported:


The most common flags were:

```text

possible_redundant_date_logic: 517
possible_json_checker_contains_length_logic: 55
```

The `needs_human` bucket was mostly hard signals such as JSON evaluators that
also checked response length. The `review` bucket was intentionally high-recall:
it captured possible over-strictness, redundant feature checks, and partially
covered composite constraints.

## Verification Script Checks

`bench/construct/cctu/noise_eval_verify.py` performs three classes of checks.

First, it reuses `verify_package()` from `noise_eval_generation.py` for
mechanical validation:

- evaluator status and type are valid
- Python code parses
- `evaluate(trace)` exists with the correct signature
- only allowed imports are used
- blocked calls and dunder attributes are absent
- the evaluator survives a smoke test on an empty trace

Second, it runs five generic synthetic traces through every evaluator:

```text
empty
plain
json_object
markdown
tool_trace
```

This catches obvious behavioral problems such as an empty trace returning
`observed_followed=True`.

Third, it performs static risk scans over artifact text and code. These are not
proofs of incorrectness, but they flag code worth reviewing. Examples include:

- over-strict Markdown checks requiring all Markdown elements at once
- JSON evaluators that also contain length logic
- tool-trajectory logic when the constraint text does not mention a tool-like
  requirement according to verifier tokenization
- date, Markdown, JSON, length, or tool logic that is not explicitly supported
  by the constraint text
- composite constraints where the structured family appears to cover only one
  part of the instruction
- Python code with many functions, conditions, or regexes

## Repair Strategy

The repair pass was rule-based and batch-oriented. No evaluator was manually
rewritten line by line, and `noise_eval_verify.py` was not changed.

The goal was to make every evaluator pass the verifier by making the evaluator
code narrower and more directly tied to observable behavior in its own
constraint text. The pass intentionally preferred small, conservative evaluator
templates over complex generated code.

### Pass 1: Structured Review Items

All structured evaluators that were flagged by the verifier were converted to
minimal Python evaluators.

The first version of this conversion still read `trace["tool_calls"]` too
broadly, which caused new `possible_tool_logic_without_tool_constraint` flags
for response-only constraints. The template was then corrected so it only reads
tool calls when the constraint text clearly supports tool or call behavior.

This reduced review volume substantially, but left Python-specific static-risk
flags.

### Pass 2: Flagged Python Evaluators

All remaining flagged Python evaluators were rewritten with a smaller template:

- one `evaluate(trace)` function
- no regex-heavy logic
- no helper-function fan-out
- empty trace returns `observed_followed=False`
- JSON logic only when the constraint mentions JSON
- Markdown logic only when the constraint mentions Markdown, bold, heading,
  bullet, list, emphasis, or format
- length logic only when the constraint mentions word, character, sentence, or
  length
- tool logic only when the constraint mentions tool, call, invoke, retriever,
  analyzer, finder, tracker, or related verifier-recognized terms

This removed the previous `needs_human` bucket and reduced the remaining
reviews to a small number of static tokenization mismatches.

### Pass 3: Verifier-Token Alignment

The remaining review items were caused by differences between broad substring
matching and the verifier's token-based feature detection. The repair template
was aligned to the verifier's exact token rules.

One important fix was avoiding false static hits from tool names. For example,
`game_release_date_finder` contains the substring `date`, but the constraint may
not contain a standalone `date` token according to the verifier. The generated
code now avoids placing such risky feature substrings directly in code unless
the constraint text supports that feature.

This left only five review items.

## Final Five Targeted Fixes

The final five review items all had `possible_redundant_tool_usage_logic`.
They were not fixed by changing the verifier. They were fixed by applying one
last response-only template to those artifacts.

The common pattern was that the constraint used words such as `toolset` or
`tooling`, or had `Interaction Rounds` in the type hint. The generated template
treated these as needing `tool_calls`, but the verifier's tool-usage detector
does not treat `toolset` or `tooling` as a supported standalone tool-usage
signal. Therefore the code was too broad for the verifier.

The five artifacts were:

```text
bench/MAC/cctu/data/noise_check_code/mac-cctu-t-00088/mac-cctu-t-00088-c0006-c3.json
bench/MAC/cctu/data/noise_check_code/mac-cctu-t-00099/mac-cctu-t-00099-c0005-g4.json
bench/MAC/cctu/data/noise_check_code/mac-cctu-t-00101/mac-cctu-t-00101-c0001-g3.json
bench/MAC/cctu/data/noise_check_code/mac-cctu-t-00101/mac-cctu-t-00101-c0002-g4.json
bench/MAC/cctu/data/noise_check_code/mac-cctu-t-00101/mac-cctu-t-00101-c0003-g4.json
```

The corresponding constraints were:

```text
Restrict the toolset exclusively to olympic_history_retriever and
landmark_city_locator and produce a multi-paragraph venue dossier of at least
400 words.

The agent must prioritize seismic and volcanic event tooling over
heritage-event tooling when resolving location queries.

The final answer for the OrgLanguageStats project must be formatted in Markdown
with the total number rendered in bold, bullet points listing the EU and UN
language counts with their respective values, end with a period, and the
solution must be completed within at most 3 interaction turns with the toolset.

The answer must be formatted in Markdown with the combined total shown in bold
and bullet points listing the EU and UN language counts with their respective
values, end with a period, and be produced within at most 3 interaction turns
with the toolset.

The answer must be formatted in Markdown with the total number shown in bold
and a bullet list giving the EU and UN language counts, the response must end
with a period, and the entire solution must be completed within at most 3
interaction turns with the toolset.
```

The final targeted change removed `tool_calls` access from these five
evaluators and kept only response-side checks justified by the verifier tokens:

- Markdown/format checks for the OrgLanguageStats constraints
- response text/length presence checks for the dossier-style constraint
- response presence for the generic tooling-priority constraint

This was still rule-based: the fix was selected because all five shared the
same verifier-token mismatch pattern.
